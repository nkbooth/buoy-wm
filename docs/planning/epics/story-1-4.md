# Story 1.4: Baseline Keybind Routing
Epic: 1 | Priority: H | Status: done

## Description
Wires the vendored `tinyrwm` keybind scaffolding in `wm/src/main.rs` to
`wm-core` for the first time — spawn a terminal, close the focused window,
cycle keyboard focus, and exit the session. This is the first story where
`main.rs`'s Dispatch handlers actually call into `WmCore` (Story 1.2's
Technical notes named this story explicitly as where that wiring starts);
everything before this point exercised `wm-core` only through its own unit
tests. Makes the WM operable at all before any picker exists.

The four keybinds already exist mechanically in the vendored code — `river`
0.4+ has no `riverctl`/compositor-side binding concept (ADR-001,
`architectural-constraints.md`: "No `river-classic`/`riverctl` command usage
anywhere"), so `tinyrwm` establishes the only mechanism this protocol
supports: the WM binds its own raw XKB keysym combos via
`river_xkb_bindings_v1`, registered per-seat in `init_new_seats`
(`wm/src/main.rs:268-290`) — `Mod4+Space` (spawn), `Mod4+Q` (close),
`Mod4+N` (focus-next), `Mod4+Esc` (exit). No new ADR is needed; this story
continues that existing, only-available mechanism unchanged. What's missing
today is that pressing them drives an entirely separate, ad hoc
`WindowManager`/`Window`/`Seat` state model in `main.rs` that has no
connection to `wm-core` at all — `wm-core`'s registries stay empty forever
in the current build. This story closes that gap for the four baseline
actions only (placement/tiling decisions are Story 1.6; tag-aware behavior
is Story 1.7).

## Acceptance criteria
**Given** the WM is running with baseline keybinds active (adapted from `tinyrwm`)
**When** I press the spawn keybind (`Mod4+Space`)
**Then** a new `foot` window opens and receives focus

**When** I press the close keybind (`Mod4+Q`) on a non-pinned window
**Then** that window closes

**When** I press the close keybind while the pinned terminal is focused
**Then** nothing happens — the pinned terminal is never closed via any routed keybind (architectural constraint, `architectural-constraints.md`)

**When** I press the focus-cycle keybind (`Mod4+N`)
**Then** keyboard focus moves to the next window in stacking order

**When** I press the exit keybind (`Mod4+Esc`)
**Then** the Wayland session ends cleanly

> **Clarification (this story, sequencing note).** The pinned-terminal
> exclusion scenario above is written and unit-tested as a pure decision
> over `wm-core` state (`WmCore::closable_focused_view`, Task 1): register a
> view whose `app_id` is the pinned-terminal app-id (`"pinned-term"`, the
> same literal `features-and-acceptance-criteria.md` and Story 1.5 use for
> `foot -a pinned-term`) and confirm the decision function refuses to
> return it as closable. That part is fully testable today and does not
> depend on Story 1.5. What genuinely cannot be exercised in this story is
> the **live** scenario — a real pinned terminal actually running,
> spawned by Story 1.5's lazy-spawn trigger, then focused and having close
> routed to it end-to-end through a real compositor. No test scenario in
> this story spawns a real pinned terminal (Story 1.5 doesn't exist yet),
> so that specific live path is structurally impossible to exercise here.
> The check is implemented defensively now, ahead of Story 1.5, precisely
> so it's already in place — see Technical notes.

## Technical notes
- Depends on Story 1.2 (`wm-core` state model — done) and, incidentally, reuses Story 1.3's `raise_view`/`stacking_order` primitives inside `cycle_focus` — no direct dependency on Story 1.3's `switch_tag` itself (tag-switching is Story 1.7's job, not this one's).
- **This is the first story where `main.rs` calls into `wm-core`.** Story 1.2's own Technical notes named this story explicitly: "Story 1.3 (switch-tag), **1.4 (keybind routing — explicitly depends on "Story 1.2 (state model)")**, 1.5 (pinned terminal), and 1.6 (floating placement) are where real compositor events start driving `wm-core` mutations." The Dispatch handlers modified: `RiverWindowV1`'s `Event::AppId` arm (captures `app_id`, `wm/src/main.rs:661`) and, indirectly through `WindowManager`'s own methods that those Dispatch handlers call, `init_new_windows` (registers the view), `remove_windows` (unregisters it), and `manage_seats`/`Seat::focus_top`/`Seat::do_action` (focus sync and the two routed decisions). No `Dispatch` impl itself needed a `wm-core` call added directly beyond the `AppId` capture — everything else routes through the existing `WindowManager`/`Seat` method layer, which is where this story's new logic actually lives.
- **New `wm-core` public API added by this story, and only this:** `WmCore::closable_focused_view(&self) -> Option<ViewId>` (Task 1), `WmCore::cycle_focus(&mut self) -> Option<ViewId>` (Task 2), and `pub const PINNED_TERM_APP_ID: &str = "pinned-term"`. No new `WmCoreError` variants — both new methods are non-mutating-on-failure queries/pure decisions, not `Result`-returning mutators (they act on internal state only, never take a caller-supplied id that could be "unknown"). `PINNED_TERM_APP_ID` is placed in `wm_core::state` specifically so Story 1.5 can import the same constant when it spawns `foot -a pinned-term`, instead of a second string literal drifting out of sync (DRY, three-strike rule doesn't apply here since this is the second use across two stories with an obvious shared meaning, not a coincidental repeat).
- **Pinned-terminal-exclusion sequencing, resolved.** `architectural-constraints.md` states "Never route a close keybind to the pinned terminal" as a standing constraint, and this story's own AC repeats it — but the pinned terminal itself (spawn lifecycle, `terminal_spawned` tracking) is Story 1.5's job and doesn't exist yet. The resolution: the exclusion is implemented as a pure app-id string comparison (`View.app_id != PINNED_TERM_APP_ID`) inside `closable_focused_view`, which needs no pinned-terminal *lifecycle* concept at all — just the same `app_id` field `wm-core` has carried since Story 1.2 and the same literal string Story 1.5 will use. This makes the exclusion **fully unit-testable today** (Task 1's `closable_focused_view_returns_none_for_pinned_terminal_app_id`, using a synthetic `WmCore` view registered with that app_id) without waiting on Story 1.5. What remains genuinely untestable in this story's scope is the *live, end-to-end* path — a real `foot -a pinned-term` process, spawned by Story 1.5's not-yet-built lazy-spawn trigger, actually focused and having a real close keybind routed at it through a live `river` session. No test scenario here can construct that (Story 1.5 doesn't exist yet), so that specific coverage gap is explicit and deferred, not silently assumed away — flag it for a human to consciously accept, consistent with how Story 1.2/1.3 treated their own NFR3/NFR1 live-compositor gaps.
- **`app_id` capture timing is an inferred assumption, not verified against a live compositor.** Task 3.3 registers a `wm-core` view using whatever `window.app_id` holds at `init_new_windows` time, which assumes the compositor has already delivered `Event::AppId` for that window earlier in the same `ManageStart` batch (a reasonable expectation — object-creation-time properties are typically sent before the management transaction that first surfaces the object — but not something the devcontainer sandbox can confirm without a real `river` session). If this assumption is wrong for some client, the registered view's `app_id` would start as an empty string and only ever hold the empty string (no `wm-core` API exists to update it post-registration — deliberately not added here, since nothing in this story's scope needs it; Story 1.6, which decides floating-vs-tiled by app_id, is the natural place to revisit this if the assumption proves false). Flagged as an assumption for review, cheap to revisit since only this story and Story 1.6 currently read `View.app_id`.
- **Single global focus vs. per-seat focus, resolved for this story.** Story 1.2's Technical notes deferred exactly this reconciliation to "whichever story first wires seat focus events into `wm-core`" — this is that story. `data-model.md`'s `View.focused: bool` is a single WM-wide flag, while `main.rs`'s `Seat.focused` is already tracked per-seat for protocol purposes. This story's `Seat::focus_top` calls `wm_core.set_focus`/`clear_focus` on every management pass for every seat, so with multiple seats the last seat processed in `manage_seats`'s iteration order wins `wm-core`'s single global focus. Accepted as consistent with the NFR framing elsewhere in the PRD that single-seat usage is the assumed common case; flagged as an assumption for review, same treatment Story 1.2 gave its own single-focus decision.
- **NFR1 (50ms budget).** Not directly benchmarked by a timing assertion — same structural-argument treatment Story 1.2 gave NFR3 and Story 1.3 gave its own NFR1 note. `closable_focused_view` is an `O(1)` lookup plus a string comparison; `cycle_focus` is `O(number of registered views)` for the `stacking_order()` copy plus two already-`O(1)`-ish existing operations (`raise_view`, `set_focus`) — both structurally far under budget, no I/O or locking involved.
- **NFR2 (panic-free).** Both new `WmCore` methods are total: `closable_focused_view` never panics (early-returns `None` on a missing focus or missing view lookup); `cycle_focus`'s two internal `.expect()`-worthy calls (`raise_view`/`set_focus` on `front`) are guaranteed to succeed because `front` was read from the same `WmCore`'s own `stacking_order()` in the same call, so implement them as ordinary `.unwrap()` (safe-by-construction, not caller-facing) rather than propagating a `Result` for a case that cannot occur through this API — document the invariant inline. On the `main.rs` side, the one `.expect()` introduced (Task 3.5, on `window.view_id`) is justified by call-ordering within a single `handle_manage_start` invocation, documented at the call site per this project's existing `.expect("... not found")` convention elsewhere in the file, and the one `Result` deliberately discarded (Task 3.4's `unregister_view`) uses `let _ = ...` rather than `.unwrap()`, per NFR2's "no empty catch blocks / no silent-swallow of errors that should stop execution" — here the discard is justified because the call path is believed structurally unreachable to fail (only this same code registers/removes the id), not because the error doesn't matter.
- **No new ADR needed for the keybind mechanism.** Checked `adrs.md` for one; none exists, and none is needed — `river` 0.4+ (ADR-001) has no compositor-side binding primitive at all (`architectural-constraints.md`: "No `river-classic`/`riverctl` command usage anywhere ... those primitives ... don't exist under `river` 0.4+"), so raw XKB keybind ownership via `river_xkb_bindings_v1` (already vendored, already wired in `init_new_seats`) is the only mechanism this protocol offers, not a choice this story is making among alternatives.
- No new Cargo dependencies.
- Build/test/lint only ever run **inside the devcontainer via devpod** (`cargo build`, `cargo test`, `cargo fmt`, `cargo clippy`) — same constraint as every prior story.

### Code Review Follow-up (2026-08-07)

Four code-review findings addressed:

- **(HIGH) Multi-seat `Action::Close` could bypass the pinned-terminal close protection.** `Seat::do_action`'s `Action::Close` arm (`wm/src/main.rs`) gated the close on `wm_core.closable_focused_view().is_some()` — a query over `WmCore`'s single, WM-wide `focused_view`. With multiple seats, `manage_seats`'s per-seat `focus_top` calls mean the last seat processed each pass wins that global field, so it can diverge from *this* seat's own real focus (`self.focused`): a real pinned-terminal focus on this seat could still pass the gate if some other seat's focus happened to currently occupy `wm_core`'s global slot, defeating the architectural constraint that the pinned terminal is never closed via a routed keybind. Fixed by dropping `wm_core.closable_focused_view()` from this decision entirely and instead looking up `self.focused`'s corresponding `Window` in the `windows` deque already passed into `do_action`, reading its own `app_id` field directly against `wm_core::PINNED_TERM_APP_ID`. This makes the exclusion correct per-seat regardless of seat count or `wm_core`'s global focus state, with no changes to `wm_core` (no per-seat focus tracking added, as directed). `WmCore::closable_focused_view` itself is no longer called from production code as a result; marked `#[allow(dead_code)]` with an inline comment explaining why (kept as public, still-unit-tested API, same narrowly-scoped-allow discipline the story already established for other not-yet-wired `wm-core` surface).
- **(HIGH) `cycle_focus`'s decision was discarded; `wm_core.stacking_order` could silently diverge from real window z-order.** Two related fixes in `wm/src/main.rs`:
  - `Action::FocusNext` previously called `wm_core.cycle_focus()` only to check `.is_some()` as a guard, then did the real work via an independent `windows.rotate_left(1); self.focus_top(windows, wm_core)` — `cycle_focus`'s own stacking-order mutation was immediately shadowed by `focus_top`'s subsequent `set_focus` call, and the two rotations could drift apart over time. Fixed: `cycle_focus()`'s returned `ViewId` is now the source of truth — `windows.iter().position(...)` finds the matching `Window` by `view_id`, moves it to the back of the real `windows` deque, then `focus_top` issues the real `focus_window`/`place_top` proxy calls against that now-correct `windows.back()`.
  - Click-to-focus (`manage_seats`'s `interacted` handling) reordered `self.windows` (real z-order) but never told `wm_core` about it, so `wm_core.stacking_order` would silently and permanently stop matching real z-order after the first mouse click, with no resync path. Fixed: the `interacted` branch now calls `wm_core.raise_view(view_id)` for the window it just moved to the back, reusing the existing Story 1.2/1.3 primitive rather than reimplementing anything. This matters ahead of Story 1.6 (floating placement), which is planned to read `wm_core.stacking_order` for tiling geometry — a divergent stacking order would have produced wrong placement there.
  - Both fixes are Wayland-glue call sites with no unit-test coverage, per the story's own established carve-out — verified via `cargo build`/`cargo clippy -D warnings` and structural tracing. The underlying `wm_core`-level interaction (a `raise_view` reorder, standing in for click-to-focus, followed by `cycle_focus` picking up from the resulting order rather than a stale one) *is* testable in isolation and was added as `cycle_focus_reflects_a_prior_raise_view_reordering` in `wm/src/wm_core/state.rs`'s test module.
- **(LOW-MEDIUM) Two `Result`s were silently discarded via `let _ = ...`.** `wm/src/main.rs`'s `remove_windows` (`unregister_view`) and `Seat::focus_top` (`set_focus`) both discarded their `Result` with no visibility into a future regression, in tension with this project's "errors propagate up, never swallowed silently" rule. Both call paths remain structurally panic-free (the ids are known-valid by call-ordering invariants — unchanged), but the `Err` arm is now logged via `eprintln!`, matching the existing pattern already used for `Action::SpawnFoot`'s spawn failure elsewhere in the same file.
- **(LOW, efficiency) `cycle_focus` did an unnecessary O(n) allocation on every call.** `WmCore::cycle_focus` (`wm/src/wm_core/state.rs`) called the public `stacking_order()` accessor (an O(n) `Vec`-cloning `iter().copied().collect()`) just to read the front element. Replaced with `self.stacking_order.front().copied()` — O(1), no allocation, same observable value. Verified via the existing `cycle_focus` tests, all unchanged and still passing. `stacking_order()` itself is now unreached from production code as a result (its only remaining caller was this one call site); marked `#[allow(dead_code)]` with the same narrowly-scoped-allow pattern, kept as public API/heavily used by tests, with Story 1.6 flagged as a plausible future production caller.

Re-verified inside the devcontainer via `devpod ssh buoy-wm`: `cargo test --manifest-path wm/Cargo.toml` (65 passed, 0 failed — 64 prior + 1 new), `cargo build --manifest-path wm/Cargo.toml` (clean, no warnings), `cargo fmt --manifest-path wm/Cargo.toml --all -- --check` (clean), `cargo clippy --manifest-path wm/Cargo.toml --all-targets -- -D warnings` (clean), `pre-commit run --all-files` (`cargo fmt --check` and `cargo clippy` hooks both passed).
