## Epic Summary

Epic 2 delivered a Unix-domain-socket IPC server inside the WM binary, a fuzzel-driven tag-manager picker (toggle and create modes, reused unmodified for tag-switching via a mode-dispatch argument), and a per-output waybar status bar module — turning Epic 1's keybind-only WM into the full multi-tag daily driver. All 5 stories (2.1–2.5) are `Status: done`, each with a Dev Agent Record and, for 4 of the 5, a Code Review Follow-up section documenting a real bug fix.

| Story | Scope | Review outcome |
|---|---|---|
| 2.1 | IPC server foundation (`get-state`, `toggle-tag`, `create-tag`, `switch-tag` over a Unix socket) | Self-caught and fixed a mutex deadlock during development, before review. Review found no crash/deadlock gaps, but caught a real bug: a set-but-empty `XDG_RUNTIME_DIR` fell through to a relative socket path instead of the documented `/tmp` fallback — fixed directly by the orchestrator (cheap, no sub-agent needed). |
| 2.2 | Tag-manager picker: toggle existing tags via fuzzel | A spike disproved the UX design's own assumed fallback (fuzzel has no native checkbox/multi-select) — resolved via explicit user confirmation of a toggle-and-reopen loop. Converted the repo to a Cargo workspace. Review found a real functional bug: the picker binary was spawned by bare name via `$PATH` (nothing populates it), so the feature would have been silently non-functional — fixed by resolving the sibling binary path via `current_exe()`. |
| 2.3 | Tag-manager picker: create-new-tag flow | Implementation agent self-committed before review ran — a process deviation, caught and corrected (all subsequent stories explicitly told not to self-commit). Review found TWO real HIGH-severity bugs in the create-then-toggle IPC chaining: an idempotent tag-name collision could silently REMOVE an already-applied tag (opposite of user intent, zero error surfaced), and a failed chained toggle after a successful create left a permanent, invisible, unapplied tag with no delete-tag API to undo it. Both required a fix-up pass plus a focused re-review, landing as a separate follow-up commit (`2bc0587`) since `08029a3`'s history had already been committed. |
| 2.4 | Wire tag-switching via picker (mode-dispatch CLI arg, reusing the picker "unmodified" per FR9) | Fixed a real gap found during drafting: the IPC switch-tag path didn't spawn the pinned terminal, unlike the raw-keybind path. Review confirmed no deadlock/double-spawn regression in the new mutex-adjacent code, but caught a real bug: `cargo test --workspace` was actually launching real `foot`/`zellij` processes as a side effect of a dispatch-layer success arm — fixed by moving the spawn out of the pure dispatch function into the IPC server's caller, verified via a live process-count check. |
| 2.5 | Per-output status bar via waybar custom module | Resolved waybar's actual custom-module mechanism via its own man pages (no live waybar/Wayland session in this sandbox — same disclosed-gap pattern every Epic 2 story carried). Review confirmed correct degradation for every disconnect scenario except one real bug: no socket read/write timeout meant a genuinely *stalled* (not just disconnected) WM would hang the status bar forever with no recovery — fixed with a bounded timeout, verified against a live reproduction of the original hang. |

## What Went Well

1. **The Epic 1 retrospective's top risk prediction held, and the team was ready for it.** Epic 1's retro named "new call sites onto existing `wm_core` mutators" as Epic 2's highest-risk category and prescribed default HIGH-priority review scrutiny plus a review→fix→focused-re-review pattern for any IPC-to-`wm_core` wiring story. Every one of the 5 stories exercised that exact pattern, and every one of the 5 found a real bug — the process was aimed at the right target from the start.
2. **TDD discipline held for all testable logic, and the testability carve-out was applied proportionally, not as a blanket excuse.** Every story kept strict RED→GREEN for `wm_core`/IPC decision logic while carving out process-spawn/socket-I/O/Wayland glue as build+clippy+manual-review-only — and Story 2.1 went further than Epic 1's own precedent by adding real Unix-socket integration tests where Epic 1's Wayland glue genuinely couldn't be tested at all. The carve-out shrank as testability allowed; it never got used to skip something that could have been tested.
3. **Self-correction inside implementation, before review even ran, happened twice.** Story 2.1 caught and fixed its own mutex deadlock during development. Story 2.4 caught its own missing-pinned-terminal-spawn gap during drafting. Both are exactly the kind of catch a retro wants to see more of — bugs prevented from ever reaching review.
4. **The Story 2.3 self-commit incident produced an immediate, durable process fix.** The moment an implementation agent self-committed before review, the orchestrator both caught it and changed the standing instruction for every subsequent story ("do not self-commit until review passes"). That rule held for the rest of the epic with no repeat incidents, and it's exactly the "orchestrator commits only after review passes" discipline the team now carries into any future work.
5. **Ambiguity was resolved with evidence or a single explicit user check, never silently.** Story 2.2's fuzzel spike is the clean case: the UX design's own assumed fallback (native multi-select) turned out not to exist, and rather than silently inventing a substitute or quietly deferring, the team got one explicit user confirmation on the toggle-and-reopen loop and moved on. No story in the epic needed a genuine `bmad-correct-course` — every ambiguity was closed with either documented reasoning or one clean confirmation, without derailing the sprint plan.
6. **Infrastructure interruptions were handled as interruptions, not treated as code problems.** Two spend-limit stops (resolved by the user raising/resetting the limit) and one transient connection-closed error (resolved by a clean retry after confirming no partial writes) all paused and resumed cleanly with zero quality impact — the loop correctly distinguished "the environment hiccuped" from "something is actually wrong."

## What Didn't Go Well / What to Change

1. **Confirmed the Epic 1 retro's prediction at a 5-for-5 hit rate — every single story's review found at least one real, confirmed bug.** This is a *higher* hit rate than Epic 1's own pattern (3 of 7 stories were clean on first review). The named risk category ("reused/modified shared `wm_core` primitive touched from a new call site") wasn't just present in Epic 2 — IPC is *inherently* that pattern for every story, since the whole epic is about giving `wm_core` a third and fourth type of caller (IPC clients, and clients-of-clients via the picker). Reviewers should treat "clean on first pass" as the surprising outcome for this class of work, not the default expectation.
2. **Two stories (2.3, 2.4) needed a fix-up pass with a follow-up commit rather than an amend, because the buggy version was already committed once.** 2.3's cause was the self-commit incident (item 4 above, already corrected going forward). 2.4's near-miss was caught before commit, but it's the same underlying pattern: real, non-obvious bugs surviving all the way to review in already-"complete" code. The Story 2.3 corrective (commit only after review passes) directly prevents a repeat of 2.3's specific failure mode, and should be treated as a permanent standing rule for any future epic, not an Epic-2-only fix.
3. **Review agents repeatedly returned incomplete first-pass reports.** Several times this epic, a review agent's first response was a brief summary rather than the full compiled findings, requiring a SendMessage follow-up nudge to get the actual final report. This wasn't a defect in the findings once compiled — every review eventually produced complete results — but it added a friction/latency tax on every story that hit it, and it happened often enough to be a named pattern rather than a one-off. **Action:** tighten the review-agent prompt to explicitly require the full compiled report as the first response, not a summary-then-nudge round trip.
4. **`devpod ssh` was unreliable for essentially the entire epic**, despite Epic 1's retro flagging it as a "sanity-check before Epic 2 starts" item. Every implementation/review agent fell back to `podman exec -u vscode -w /workspaces/buoy-wm bold_vaughan <cmd>`, which worked reliably throughout. The Epic 1 ask to "sanity-check it" wasn't enough — the tool stayed broken across a full epic while a working substitute was used every single time. **Action:** either fix the underlying `devpod ssh` transport issue, or stop treating `podman exec` as a fallback and formally adopt it as this project's primary verification path — the data says it's the reliable one.

## Handoff to Final Retrospective

This is very likely the last epic-level retrospective for this project — Epic 2 is the final epic, and no Epic 3 exists. Two patterns from this retro are epic-spanning rather than Epic-2-specific and belong in the project-level retrospective too, not only here:

- **The `devpod ssh` unreliability** was first flagged in the Epic 1 retro and never actually resolved across two full epics, only worked around. A project-level retro should record `podman exec` as the de facto verification path this whole project actually used, rather than let the "sanity-check it" action item quietly die a second time.
- **The review-scrutiny-on-shared-mutators pattern** (named in Epic 1's retro, validated at a 5-for-5 hit rate in Epic 2) is a project-wide lesson about this codebase's specific risk shape (a small, shared, mutex-guarded core state object with a growing number of call sites), not an Epic-2-only finding — worth stating as a general engineering principle for any future work on `buoy-wm`, not just as an Epic 2 retro note.

Everything else in this retro (the Story 2.3 self-commit correction, the create-then-toggle bug class, the specific bug list per story) is Epic-2-scoped and doesn't need to be repeated at the project level beyond a brief summary reference.
